# 「升维」规则的科学性审查

审查对象：`~/.dsh/AGENTS.md` §5「Proactive Depth Elevation Prompting（主动升维询问机制）」，以及把它硬化成插件的 `dsh-depth-elevation`。
方法：把规则当作一个二分类判据（diagnostic classifier）来评分——这是它自己声称的身份（"硬判据"），因此可以用判据的通行标准检验，而不需要作者配合。
数据：本机 148 份真实会话、334 条非空人类消息、300 个有真人输入的 turn。
脚本在 `docs/analysis/`，每个结论都可复现。

---

## 结论

**规则的内在逻辑是自洽的，但它声称的预测对象未被任何数据支持。** 四项独立检验：

| 检验 | 结果 | 含义 |
|---|---|---|
| 判别力（4 种深度定义） | 三个 AUC **≈0.51 / 0.52 / 0.47**；第四个（是否产出文件）两组比例几乎相同 | 等价于抛硬币 |
| 用户验收率 | **3/5 升维、2/5 直接做** | 60%，n=5（样本不足，见边界说明） |
| 承诺的四步法是否执行 | 3/3 升维案例**均未**重写提示词 | 机制名义上存在 |
| 可证伪性 | 无精度目标、无样本量、无推翻条件 | 不可证伪 |

**一句话**：这是一个**意图声明**被写成了**判据**的样子。它在「让模型别自作主张跳过」这个目标上是有效的（插件实测 5/5 服从），但它在「识别有深度的任务」这个目标上是无信息的（四种判准里三个 AUC 0.470–0.516，第四个两组比例几乎相同），而规则文本把后者当成了前提。

---

## 一、先说它做对了什么

不能只挑错。规则有三处是真正扎实的：

**1. 「禁止模型自行判定任务琐碎」这一条，方向完全正确。**
这是整条规则最有价值的部分，而且有数据支撑：prompt-only 时模型触发率 4%，插件硬化后 5/5 服从。模型确实会在「这个规则会不会烦到用户」上做自我审查，并且审查结论对自己有利。把这个判断权从模型手里拿走，是对的。

**2. 触发用硬判据而非「重要性」裁量，方向也正确。**
「重要性」是不可操作的谓词，交给模型等于交给它自由裁量。换成「含文件路径/含这些动词/≥150 字」这样的可机械判定条件，至少在**可复现性**上是对的——同一句话每次得到同一结果。

**3. 「先弹窗、别先干活」的时序约束，是对的。**
如果允许先探索再决定是否升维，模型会用「我已经看了，这任务挺简单」来合理化跳过。这个约束堵住了那条路。

这三条是规则的骨架，而且是好的骨架。问题出在别处。

---

## 二、问题一：判定阈值（clauses a–d）不具备它声称的判别力

规则说「首轮输入命中任一条即必须触发」，隐含前提是：**命中 = 这个任务有深度**。这是关于一个判据（classifier）的陈述，所以可以用判据的标准评：

- 正样本：需要大量工作的 turn
- 负样本：不需要的
- 指标：AUC（0.5 = 无信息，0.7 = 可用，0.8+ = 强）

「需要大量工作」我用了四种可操作定义，全部来自语料，与规则无关：

| 判准 | 规则命中 vs 未命中的 AUC |
|---|---|
| C1 turn 内 step 数 > 中位数 | **0.509** |
| C2 是否产出文件 | 命中组 26/80，未命中组 35/123（几乎相同） |
| C3 该任务后续需要几轮追问 | **0.516** |
| C4 turn 实际耗时 | **0.470** |

四个判准，三个落在 0.5 附近，一个甚至反向。**规则识别不出它声称要识别的那个量。**

> 数字会随语料增长小幅漂移（本文写作时为 0.509，重跑得到 0.510）。漂移方向不重要——重点是它们始终贴着 0.5。任何一次重跑得到 0.7 以上，这个结论就要重审。

（AUC 实现已用已知答案自检：完美 1.000、反向 0.000、常数 0.500、并列 0.875，全部符合手算。）

**另一条独立路径的交叉验证**：不用匹配器预测，直接看**真实触发过**的 turn。203 个正常完成的 turn 里，8 个被真实弹过窗，195 个没有：

```
被弹窗的 8 个 turn：4 个工作量高于中位数  (50%)
未弹窗的 195 个   ：96 个高于中位数        (49%)
```

50% vs 49%。两种完全不同的算法——一个用匹配器打分，一个用磁盘上真实发生的事件——给出同一个结论。这不是统计功效不足，是**没有效应**。

### 我一开始以为是混淆变量，排除后结论不变

第一版测出「命中子句的 turn 反而更短」（4 vs 8 steps）。这显然是混淆——失败的 turn 步数就少，而 provider 报错在本机极常见。限制到**正常完成的 turn** 后：

```
hit : median steps 14.0
miss: median steps 13.5
ratio: 1.04
```

差异消失了。也就是说，一旦控制掉「挂掉的 turn」，规则命中与否对工作量**没有影响**。

### 补充：动词的基率高得离谱

单看 (b) 子句的触发词在普通对话里的出现率：

| 动词 | 出现率 |
|---|---|
| 分析 | 6.9% |
| 设计 | 6.6% |
| 方案 | 5.4% |
| 整理 | 2.1% |
| 优化 | 1.8% |

这三个词单独看都只有个位数百分比，但它们是「分别出现」的比率，实际（b）子句整体的命中率是 **15.3%**——也就是说每 6~7 条人类消息就有 1 条触发。一条判据若在六分之一的输入上报警，它必须先证明这 1/6 确实比其余 5/6 更值得走专家流程。数据说它没有（AUC 0.509）。

### 为什么这条重要

规则里写的是「**让用户不必记长提示词**」。但如果判据捕获不到任务的实际体量，那么它对「哪些任务值得走专家流程」这个决策就没有信息量——它只是在给大约 31% 的消息挂上一个和任务体量无关的标签。

## 三、问题二：四个子句的贡献差 33 倍，其中一个基本是装饰

如果四条判据是独立证据，命中两条应当比命中一条更可信。实际共现矩阵（334 条人类消息）：

```
           a       b       c       d
(a)        6       4       5       1
(b)        4      51      15      34
(c)        5      15      54      14
(d)        1      34      14      48
```

（更正：这一矩阵我第一版算错了——错误地把「该子句命中率」填进了共现格，得出 (a) 行 18/7/10/6。正确做法是数同时含两个子句的消息。现为复算后的值。）

关键数字：**P(d | b) = 34/51 = 67%**。命中动词的消息里，三分之二同时也命中「帮我/给我/生成」这类交付请求。因为中文里「帮我分析一下」同时是动词 + 交付请求，这两条在同一个语言现象上重复计数。

要判断某个子句「有没有用」，正确的问法是**删掉它会损失多少**（delete-one-clause），而不是数它命中了多少次——命中了但别的子句也会命中的，删掉它并不损失任何覆盖。

| 子句 | 删掉它损失的命中 | 占全部命中 |
|---|---|---|
| (a) 路径/代码块/表格 | **1** | 1.0% |
| (b) 触发动词 | 11 | 11.0% |
| (c) 长素材/链接 | 33 | 33.0% |
| (d) 交付请求 | 9 | 9.0% |

（100 条被任一子句命中的消息，334 条人类消息。）

**结论比我初稿更尖锐**：(a) 几乎完全是冗余的——删掉它只损失 1 条消息。它之所以在规则文本里显得重要（「含文件路径、代码块、表格」），是因为这些特征在真实中文对话里几乎总伴随 (b) 或 (c)。它是个**看着像判据、实际是装饰**的子句。

(c) 是主力（33 条），(b) 和 (d) 各贡献约 10 条，(a) 贡献 1 条。规则把它们并列为「任一条即必须触发」，读起来像四个独立理由，实际的相对权重差 33 倍。

## 四、问题三：没有精度目标，也没有推翻条件

这是最根本的一条，也是最容易修的一条。

规则目前的状态：

| 要素 | 规则里怎么写 |
|---|---|
| 精度目标 | **未定义** |
| 可接受误报率 | 「宁可多弹一次，不可静默跳过」——**无上界** |
| 需要多大的样本才敢下结论 | **未定义** |
| 什么观察结果会让你推翻或修改这条规则 | **未定义** |

一个没有推翻条件的规则，不是判据，是偏好。它无法被数据纠正，因此也无法被你自己的经验改进。

对比：一条科学表述的判据会长这样——「命中子句的任务，其中 ≥70% 应当在用户点选后实际走入专家流程；若连续 20 个命中任务里升维选择率低于 40%，则该子句需要重写」。

这样写才有可被证伪的形状。

### 验收率数据（n=5，样本严重不足）

用户的手动选择是唯一独立于规则的判准：

| 结果 | 次数 |
|---|---|
| 选「升维」 | 3 |
| 选「直接做」 | 2 |
| 未回答（turn 报错/中断） | 20 |

验收率 60%。**但 n=5，不能拿来说事。** 这本身才是发现：这条规则把「用户会不会想要升维」当作核心决策，而这个量的实测样本只有 5 个。

## 五、问题四：承诺的四步法实际没有执行

规则明确写了：用户选「升维」→ **立即执行四步法，用工业级标准重写提示词再落地**。

三个真实的「升维」案例，模型的实际反应（原文摘录）：

案例 1：
> `User chose 升维. Now I need to do the four-step... Then execute. First, let me explore the workspace.`

案例 2：
> `User selected 升维 (elevation). Now I need to follow the four-step method: ... But first — the user said "帮我分析这份台账" ... They didn't attach a ledger!`

案例 3：
> `User chose 升维. Now I need to do the four-step method... But practically, I need to read the working directory materials.`

**三个案例都口头复述了四步法，然后直接开始干活，没有重写提示词。** 用正则搜索「重写/重构后的提示词/revised prompt」等信号，命中率 0/3。

这不是模型不听话——它确实记得要做四步，但「①顶级专家未想之策 ②原始底层素材 ③专业工具与模型 ④客观外部裁判标准」这四步**没有可执行的定义**：它说不清「做完这四步」和「没做这四步」的区别，所以那句「立即执行四步法」在实践中退化成了一句自我声明。

**这解释了为什么规则在「服从」这一维上 100% 有效、在「效果」这一维上无从验证**：它强制执行的是一个**动作**（弹窗），而不是一个**标准**（重写后的提示词该长什么样）。

---

## 六、问题五：代价没有预算

「宁可多弹一次」隐含「弹一次的成本可忽略」。实测不是零：

| 成本项 | 实测 |
|---|---|
| 注入的指令长度 | 412 字符 ≈ 137 tokens |
| 该消息生命周期 | 作为 surface user/message 保留，**后续每一步都重发** |
| 每个被拦 session 平均后续 step | 44.5 |
| 折合 | **~6000 tokens / 次拦截** |
| 额外往返 | 被拦后先 ask，再干活，多 1 轮 |
| 弹窗后用户真答了 | **5/25**（另 17 次 turn 在弹窗前就被 provider 报错打断，3 次旧 hook 用纯文本假装弹窗） |

单次几千 token 不算大，但它是**持续性**成本，而且规则的「多弹无妨」写法说明这个成本从未被计入。如果一条规则声称「宁可误报」，它至少应当声明误报的代价上限。

这里必须把两类成本分清，否则会得出错误结论：

- **规则的代价**：137 tokens × 该 session 后续步数 ≈ 6000 tokens，这是规则本身带来的，可归因。
- **不是规则的代价**：25 次弹窗里 17 次之后 turn 直接因 provider 报错（429 / oauth 失效 / 无适配器 / 余额不足）终止。这是我的模型供应商问题，不能算到规则头上。我在初稿里把它们一起算成了「未回答 76%」，那是错的。

真正能归因于规则的浪费形态是第三种：**3 次纯文本假弹窗**（旧 hook 时期，工具列表里没有 `ask_user_question`，模型却被告知必须调用它，只好用 markdown 假装弹窗）。这 3 次是规则与运行环境不匹配导致的确定性浪费——插件版本已经把这一条治好了（加入「批次里必须有人类消息」和「subagent 不拦」两个守卫）。

## 七、问题六：文档与实现不一致，且用户只同意了文档

规则文本列了 13 个触发动词。插件实际用了 **28 个**：

```
规则文本未包含的 15 个：
汇报 梳理 汇总 整理 编写 制定 优化 诊断 材料 创建 开发 实现 做一个 写成 整成
```

这不是 bug——扩展有理由（replay 发现漏拦）。但**用户同意的是 §5 那份文本，而实际执行的是更宽的一套**。在「硬判据」这个语境下，这个差异值得明确：哪些是规则的要求，哪些是实现的选择。

另外：`OFFER_MARK` 让指令文本自身抑制后续拦截（防止重复弹窗，合理），但这意味着**任何评估「该触发多少次」的分析，都会被规则自己的输出污染**。本机语料里污染是 0%（334 条人类消息无一带该标记），但这只是因为我的分析排除了注入消息；换个口径就会撞上。

## 八、这份规则真正的正确写法

不是推翻它，是给它装上它缺的那几个零件。四个改动：

### 1. 把「判据」降级为「筛选器」，并声明精度目标

现在它假装是判据（命中 = 有深度），实际只能做筛选器（命中 = 值得问一句）。改：

> 命中子句只表示「可以问」，不表示「应当升维」。目标：命中任务中升维选择率 ≥ 50%。

这一句就把规则的自我认识修正到与数据一致，且立刻可验证。

### 2. 给四步法写成可判定的验收条件 —— **已实施**

「立即执行四步法」之所以退化成口号，是因为四步没有产出物定义。已改为：

> 选择升维后，第一个动作必须是在回复中给出**重写后的提示词全文**（含：①验收标准 ②原始素材清单 ③方法与工具 ④外部裁判方式），然后才开始执行。**复述这四步而不产出这个文件，不算执行。**

改动落在 `lib/decide.js` 的 `instructionFor()`（R13 断言其存在），测量器是
`test/_elevation_fidelity.py`。

**但必须说清楚：这只是把「可执行」变成了「可检查」，还没有证明它有效。** 目前
`--stats` 里 `new` 一行为空——本机所有升维案例都发生在指令改动之前，没有一条
实际受到新约束。

`test/_fidelity_corpus.py` 补上了这一段的空白：它按 harness 的真实落盘形状
（`<root>/<workspace>/<session>/session.v4.jsonl.zstd`，zstd 压缩的 JSON lines）
造一批 post-R13 合成会话，通过 `DSH_FIDELITY_SESSIONS` 指给扫描器，端到端验证：

| 检查 | 结果 |
|---|---|
| 行数与预期 | 7/7 |
| era 归属正确（new vs legacy） | 通过 |
| 种植的 pass/fail/no-reply 精确复现 | 通过 |
| `直接做` 不产生行 | 通过 |
| 只在 reasoning 里提四步 → fail | 通过 |
| `--stats` 报出的通过率 = 种植比例 | 40%（2 过 / 3 败 / 1 无回复） |
| `no-reply` 计入但排除出分母 | 通过 |

并且用**变异测试**确认这个验证器有判别力：把「需全部四部分」改成「有一即可」→ 测试失败；
把 era 判定改成「永远是 new」→ 测试失败。

**但这仍然不是「这条规则有效」的证据。** 它证明的是：当真实 post-R13 语料出现时，
统计器会正确地把它算出来，而不是静默返回 0 或把无回复算进分母。规则是否真的让模型
产出产出物，仍然只能是未来语料说了算——把「仪器准」读成「结论对」是这一类
改正最容易犯的错。

### 3. 定义推翻条件

分两层，因为「规则错了」和「某条子句多余」是不同的失败：

> **规则级**：连续 20 个命中任务中升维选择率 < 40% → 整条规则需要重写。
> **子句级**：某子句的独立贡献（只有它命中、别的子句都不命中的消息占比）< 5% → 该子句应合并或删除。

按子句级标准实测（delete-one-clause 定义）：(a) 只损失 1.0% 的覆盖，远低于 5% 阈值，**应当删除**；(b) 11.0%、(d) 9.0% 在线上**应当保留**；(c) 33.0% 是主力，**必须保留**。

这个例子本身就说明为什么要写清推翻条件：没有阈值时我判不了 (a) 和 (d) 该不该动，有了阈值才能给出可复算的结论。

### 4. 给误报定个上限

「宁可多弹一次」改成「误报率目标 < 30%，实测上限见回放」。有上限才叫策略，没上限叫偏好。

## 九、需要说清楚的边界

这份审查的局限，避免过度解读：

1. **样本来自一台机器、一个用户、3 周**。334 条人类消息里真正带升维交互的只有 5 条。AUC 结论建立在 203 个完成 turn 上，是够的；验收率结论建立在 5 个样本上，**不够**。
2. **「深度」没有客观金标准**。我用工作量/产出/追问轮数/耗时四种代理指标，都接近 0.5。这不排除存在我没想到的第五种定义，能让规则看起来有判别力——但一个规则若要成立，作者应当指明是哪种定义，而规则文本没有指明。
3. **AUC 0.5 不等于规则有害**。它的代价是「多问一句」和几千 token；收益是「不漏掉该问的」。这个交换在**用户明确选择接受**的前提下是合理的——问题只在于规则把它说成了判据，因而免除了被检验的义务。
4. **插件侧的成效是真的**。5/5 服从率、0 无法解释的漏拦、0.4% 误拦——这些是硬化这条规则带来的、可验证的改进。规则本身的问题和插件实现的质量是两件事。
